# sk-milestone

Milestones are releases. One opens with an outcome sentence. It closes with an audit against it, a check of the release as a whole, a version tag, and a GitHub Release.

A sealed reviewer reads the scope at Opening and the release at the close. Both moments run only where `sidekick pm board` reports `tracked: true`. Grooming between the two is not this skill's; it is tracked separately.

## Opening

1. The outcome sentence comes first: what will be true when the milestone closes. Agree it with the operator, then the scope in a line or two. Size the milestone by that outcome: the smallest release that makes the sentence true.
2. Create it from a file, so line breaks reach GitHub as written. Write `Outcome: <sentence> Scope: <lines>.` to a file, then run `gh api -X POST repos/<owner>/<repo>/milestones -f title="<title>" -F description=@<file>`. There is no `gh milestone` command.
3. Seed scan: list the open `backlog` issues with `gh issue list --label backlog --state open --limit 200`. For each, read its `Revisit when:` line and ask whether the condition now holds. Propose the ones that do; nothing moves without agreement. An accepted seed loses the label and gains the milestone: `gh issue edit <n> --milestone "<title>" --remove-label backlog`. Then list the designs whose `docs/designs/<topic>/design.md` status line reads `ready for PM`, and propose them the same way. An accepted design is filed through `sk-track`, one issue per piece of its breakdown, into the milestone. Its status line becomes `planned (#NN, …)`, and the index of each research topic it cites names the same issues.
4. Group the milestone's issues into plans. Each is a logical group sized to what one session holds, so a session starts and ends cleanly. Name each plan by its content, never by a letter or a number. List the plans in the order to take them: the header's order is the run order, so the description needs no separate `Order:`. Once the grouping is drafted, dispatch `sidekick:sk-holistic-reviewer` as `references/scope-review.md` says. Present its review beside the grouping, with your answer to each finding, for one ruling. An issue that fits the repo but not this milestone returns to `backlog`. One that does not fit the repo closes `not planned`. `references/scope-review.md` §Answering gives both. Then write the plans header at the top of the description's file, before the outcome:

   ```
   <!-- plans -->
   1. <name> (#N, #N)
   2. <name> (#N)
   <!-- /plans -->

   Outcome: <sentence> Scope: <lines>.
   ```

   `sidekick pm` reads plans from this header alone, and never from the prose after it. PATCH the whole description from the file: `gh api -X PATCH repos/<owner>/<repo>/milestones/<n> -F description=@<file>`. A `PATCH` replaces the whole field, so the file carries the description in full. The grouping comes last because a design's breakdown gets its issue numbers in step 3. After Opening, a regroup or an addition first writes the live description to the file:

   ```
   gh api repos/<owner>/<repo>/milestones/<n> --jq .description > <file>
   ```

   Then edit its header and PATCH it with the step's `PATCH` command, with a comment on each moved issue saying why.
5. Tell the operator the milestone, its outcome, its plans, and what it opened with. The scope is now what the description names, and later additions follow `sk-pm-conventions.md` §Change control. Post the first status update, `ON_TRACK`, as `sk-orient` §Status updates says, naming this milestone. Then orient: the first pickup comes from the board. While another milestone stays open, `pickup` names whichever of the two alone holds In Progress cards. When neither does, or both do, the brief lists both, and the operator chooses.

## Closing

1. `sidekick pm gate --milestone "<title>"` says whether anything is still open, and `sidekick pm lint` says whether the board is clean. Every open issue is dispositioned before anything else. It is carried into the next milestone with a reason, closed `not planned` with a verdict, or returned to `backlog` with a `Revisit when:` line. Every lint finding is fixed or named. A disposition that leaves work out of the release is the operator's decision: ask when it arises, and write it on the operator's yes. Filing that keeps work in the release runs as it arises, as `sk-track` files.
2. Audit against the outcome sentence: for each clause, what shows it is true? A clause without evidence is a gap, and each gap gets an issue or an explicit judgment that it did not matter. A gap left for later is the operator's decision, asked when it arises and written on the operator's yes. An issue that keeps the gap in the release is filed as it arises. When its fix ships in this release, the close waits for it, and step 1's gate runs again once it closes. The extension test applies here. A milestone extends only for must-haves that survived scope-cutting and carry no remaining unknowns; everything else belongs to the next milestone. The audit also lists each `docs/designs/<topic>/` whose status line reads `planned` and whose issues have all closed. It lists the issues added after Opening too, so each addition is visible at the close. An addition carries the comment `sk-pm-conventions.md` §Change control asks for. Without one, `gh api repos/<owner>/<repo>/issues/<n>/events` dates the issue's `milestoned` event against the milestone's `created_at`. Opening's own filings follow `created_at` within its session, and a later join is an addition.
3. Check the release as a whole, as `references/release-review.md` says: three sealed reviewers read everything the release ships, for agreement, completeness, and fit. Confirm each finding at its source, and fix every confirmed one before the release. A fix is consistency work, so it is no addition, and neither `sk-pm-conventions.md` §Change control's deferral nor the extension test applies. A finding too large for this session is posted `AT_RISK`, as `sk-orient` §Status updates says, and the operator chooses an added plan or backing out its cause. Run step 1's gate again after an added plan.
4. Decide the learning record here, because the release commit carries it. The bar is a counterfactual: without the record, would the next engineer repeat the mistake or redo the investigation? Then prepare the release locally, and leave it uncommitted. When the record clears the bar, write it. Write it where the docs layout's §learnings/ puts it, in the shape it gives: `../sidekick/references/docs-layout.md`, relative to this skill's base directory. A repo's own README overrides that section, in its learnings folder or in `docs/README.md`. Delete the design folders the audit listed. Run the preparation of the repo's release, as step 5 describes, and the repo's gates. When fixes landed in step 3, run the check's re-check after the preparation, as `references/release-review.md` §The re-check says. Draft the release notes from the audit, issue by issue, with a link to the record when there is one. Add the release check's section, as `references/release-review.md` §The record says. Keep them on a path git ignores, or outside the repo, because a tag step may refuse a dirty tree. Present these to the operator: the dispositions, the audit, the version, the record judgment, the diff, the gate results, and the notes. Add the check's findings with their confirmations, drops, fixes, and re-check. Say how to undo the preparation, and ask. The ask covers the release alone. From the release's commit on, everything waits for a yes; of the release, only this reversible, local preparation runs before it.
5. Run the release, then close the milestone. The repo's release is the one its guidance states, in `AGENTS.md`, `CLAUDE.md`, or a doc they name. Follow it in full and in its order. Its preparation, the local steps before its commit, ran in step 4, and its publication runs now. Where the guidance states none, use the default release. Its preparation bumps the version where the repo keeps it, such as `package.json`. Its publication commits everything step 4 prepared and lands the commit by the repo's route. That route is the one `sk-execute` integrates a branch by: a push, or a pull request merged before the tag. It tags the commit that landed with `git tag -a <tag> -m "<title>" <commit>` and `git push origin <tag>`, where `<tag>` is `v<version>` unless the repo's existing tags follow another form. Then it runs `gh release create <tag> --verify-tag --title "<repo> <version>" --notes-file <notes>`. Whichever release runs, its commit carries the record and the deletions. After its last step, post the closing status update, `COMPLETE`, as `sk-orient` §Status updates says, naming this milestone. Post it while the milestone is still open, since `pickup --report` reads only an open one. Last, `gh api -X PATCH repos/<owner>/<repo>/milestones/<n> -f state=closed`.
6. Comment `Resolved in <version>.` on each issue the milestone completed, so an issue says which release carried it. List them with `gh issue list --milestone "<title>" --state closed --limit 200 --json number,stateReason` and keep only `stateReason` `COMPLETED`. A `not planned` close gets no comment. GitHub relates a milestone to a release nowhere; the comment is that link.
7. Tell the operator what shipped, in one line, and orient again: the next milestone opens from the board.
