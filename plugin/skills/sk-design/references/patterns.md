# Pattern index

Problem shapes that recur, the patterns worth weighing for each, the question that decides between them, and what each costs. It is an index, not a menu: the pattern card still has to say why a pattern applies here and where it already appears. "No pattern" is a row because most problems are local. A repo's own rules may add rows for its domain.

| Problem shape | Candidates | The deciding question | Cost, and when not |
|---|---|---|---|
| A switch or if-chain picks among similar implementations by a discriminator (`provider`, `channel`, `type`) | **Strategy**: one interface, one object per variant. **Registry and factory**: variants registered by key, chosen by data. **Table-driven dispatch**: a map from key to function. **Discriminated union with an exhaustive switch**, when the variants are data and the set is closed | Is the set of variants open, added by config or a new package, or closed and known at compile time? Do variants carry state or a lifecycle, or is each one function? | A registration step and a "not found" path, and one more file per variant. Not for two variants with no third in sight: the third occurrence is when the abstraction becomes mandatory |
| A second source or target of a kind that already exists: a tracker, a channel, a provider | **Adapter**: normalise in, denormalise out, one per vendor. **Port and adapter**: the core speaks domain vocabulary, and vendors live at the edges | Does the core already speak the first vendor's names? If it does, the port is the finding, and the second vendor is when you name the domain's own terms | A translation layer to keep in sync, and a legacy variant while stored data migrates |
| Multi-step work across services or tables that must not half-complete | **Saga**, orchestrated or choreographed, with a compensation per step. **Transactional outbox**: the event is written with the state change, and a relay publishes it. **Idempotency keys**. **One database transaction**, when every step lives in one database | Can each step be compensated, or must the whole be atomic? Who needs to see a half-done state, and where? An orchestrator gives one place to look; choreography gives none | Compensation logic per step, and eventual consistency visible to readers. The outbox needs a relay, and the consumer needs a dedupe |
| A record with a lifecycle, its status mutated from several places | **Explicit state machine**: states, transitions, guards, and one place that applies them. **Event-sourced projection**: the log is the truth, and the status is derived and rebuildable | Who writes each field, and can the state be rebuilt from events? If two lifecycles share one record, split the record before adding states | A transition table to maintain. Projections lag and need a catch-up path |
| The same external call may run twice: a retry after success, a duplicate webhook | **Idempotency key**, or a **natural key with upsert**. At-least-once delivery with a dedupe on the consumer | Is there a natural key, such as a delivery id? If not, mint one before the first call and store it with the intent | A key store and its retention. Never "exactly once" across a network; design for the duplicate |
| Several parts must react to one occurrence | **Observer**, or an **event bus** when publishers and subscribers should not know each other. A **direct call** when there is one consumer | How many consumers are there, and must the publisher know them? Does a consumer's failure affect the publisher? | Hidden control flow, and ordering and delivery to design for. Not for one consumer: a direct call is clearer |
| A cross-cutting concern creeps into every function: logging, timing, retries, auth, budgets | **Decorator, middleware, or interceptor** at one boundary: the request path, the tool-call path, the client | Is the concern uniform, or configured per call? Uniform goes in one wrapper; per-call goes in the options of the thing wrapped | Hidden control flow: a reader has to know the wrapper exists, so name it where the wrapped call is made |
| A component with several collaborators, some optional | **Factory function with an options object**, failing fast on the required ones. Never a service locator or a module-level global | Is the collaborator required for the instance to be valid? Then it is a constructor argument, and its absence is an error at construction | An options type to keep honest. The factory is a function, not a framework |
| A function steered by booleans or a long parameter list | **Parameter object**. **Discriminated options**, such as `{ mode: "a", … } \| { mode: "b", … }`. **Separate functions** when the flags never combine | Do the flags combine independently, select one of a few shapes, or never combine? | A type to keep in sync with the call sites. Not for a single boolean with one call site |
| An expensive, rate-limited, or flaky dependency | **Backoff with jitter** and a status classification: retry 5xx and 429, fail fast on other 4xx. **Circuit breaker**. **Bulkhead**: a bounded pool. **Cache with explicit invalidation** | What should the caller experience while it is down: wait, fail fast, or degrade? Decide that first, and the pattern follows | State to hold, such as breaker state or pool size, and a way to see it |
| Code that must accept future kinds without edits | **Registration and declarative configuration**: a registry the new kind adds itself to, or a config file the registry discovers. A **plugin seam** when kinds arrive from outside the repo | Is the variation data or code? Data goes in config a registry discovers; code goes behind an interface the registry loads | A discovery step, and a validation schema at load. Not when the set is closed and small: an exhaustive union is cheaper, and the compiler checks it |
| Data read or written across a package or service boundary | **Schema at the boundary**: parse, don't validate. **Versioned or additive contracts**: add a field, never change its meaning. **One owner per schema** | Who owns the schema, and can the other side deploy on its own schedule? If it can, every change is additive first, and the old shape keeps parsing for a release | A second copy of the type on the reading side. Do not share a package to avoid the copy if it drags its dependency tree along |
| Two implementations, a local problem, a change inside one module | **No pattern**: a plain function, a lookup table, a well-named module | Would a reader need a second file to understand this? If not, a pattern adds a second file for nothing | Every pattern costs the reader a second file. Take the seam, an interface with one trivial implementation, only where change is known to come |
