# Probes: assumed constraints and memory experiments (2026-10-12)

The design note listed three constraints as assumed and three experiments as owed. Each was run on the operator's machine, in the sidekick repo or a scratch folder. Probes ran on Haiku 5.5 to keep them cheap.

Provenance grades follow the companion reports:

## Constraint: a mod's status shows beside a custom status line

**Holds, measured.** A probe plugin with one hooks module called `$.ui.status('MODPROBE-STATUS-42')` on `session.start`. It ran in a `claude --bg` session beside the operator's GSD `statusLine` command. Replaying `claude logs` through a terminal emulator (`pyte`) gave the final screen's last lines:

```text
  ⚠ modprobe: MODPROBE-STATUS-42
  Haiku 5.5 │ sidekick ░░░░░░░░░░ 8%
```

- The mod's line sits directly above the custom status line, and both stay drawn.
- The engine prefixes the text with `⚠` and the plugin's name, so a mod does not control the line's whole look.
- Docs: the bundled types say `status` "Pins `text` as this plugin's status line under the prompt, beside the engine's own pinned notices". They allow one line per plugin.
- `hooks.json` takes `modules` as an array with one entry; `claude plugin validate` refuses a string.

## Constraint: a background session takes a slash command as its first prompt

**Holds, measured.** `claude --bg -n cc-probe-slash "/sidekick:sidekick In one sentence, …"` ran in the sidekick repo. Its transcript records the prompt as a command, `<command-name>/sidekick:sidekick</command-name>`, followed by the skill's body as a meta message. The session answered from the skill text.

## Constraint: a profile loads a shared notes file read-only

**Loading holds; read-only holds against Claude Code's own tools only, measured.**

- `--append-system-prompt-file <notes>` put a canary line in the system prompt, and the session quoted it back without tools.
- With `permissions.deny: ["Edit(//<abs>/shared/**)"]` in `--settings`, under `--permission-mode bypassPermissions`:

| Write attempt | Result |
|---|---|
| Edit tool | refused: "File is in a directory that is denied by your permission settings" |
| Bash `echo … >> notes.md` | refused |
| Bash `echo … \| tee -a notes.md` | refused |
| Bash `python3 -c "open(…,'a').write(…)"` | **succeeded** |
| Control, no deny rule: Bash `echo … >> control.md` | succeeded |

- A deny rule therefore keeps the model's ordinary file tools off a path. It is not an enforcement boundary against code the session runs.
- `Write(path)` deny rules are not matched by file permission checks. Claude Code said so at start: "only Edit(path) rules are … Edit rules cover all file-editing tools".
- Not tested: the `sandbox` settings, or file-system permissions, as a harder boundary.

## Experiment: `autoMemoryDirectory` in a profile

**Holds, measured: writes and the startup index in headless sessions, writes in background ones.** Two `claude -p` runs passed `--settings '{"autoMemoryDirectory":"<scratch>/memA"}'`.

- The first, in a scratch folder, saved a note. It wrote `probe-colour.md` and a new `MEMORY.md` into the scratch folder.
- The second ran in the sidekick repo. Its transcript holds the scratch index's line once and sidekick's own index not at all; `r9-exploration-2026-10` appears zero times.
- No file in sidekick's memory folder changed.
- In default permission mode the first session's `ls` and `grep` were refused, while its writes to the memory folder went through.
- The next experiment set the same key on two `--bg` sessions, and their writes landed in the scratch folder. Whether a background session's startup index comes from that folder was not checked.

## Experiment: two background writers on one memory folder

**No update was lost; Claude Code's file tools carry a precondition, measured.**

Two `claude --bg` sessions in the sidekick repo shared one scratch memory folder through `autoMemoryDirectory`. Each saved six notes, one at a time, adding an index line after each.

- All twelve notes and all twelve index lines landed. The two sessions' writes interleaved between 13:26:27 and 13:27:01, and overlapped from 13:26:39 to 13:26:45.
- Each session anchored its `Edit` on its own last index line, so the other's lines stayed. Writer A's block landed between writer B's second and third lines.
- When the file had changed since the session read it, `Edit` still applied. It returned a note: "the file had been modified on disk since you last read it — the edit applied cleanly, but the file contains other changes not in your context."
- `Write` refuses in the same case. In this session a `Write` after another process appended returned "File has been modified since read … Read it again before attempting to write it."
- Memory writes outside the repo did not move either session into a worktree; `git worktree list` showed only `master`.

What this does not show: a race inside one `Edit`'s own read and write, which one run cannot rule out. Nor does it cover writes through Bash, which skip both checks. Two sessions saving the same fact as two notes, or contradicting each other, is a different failure that this experiment did not try.

## Experiment: audit of one memory folder

**Judged, by a read-only subagent, on sidekick's folder** (`~/.claude/projects/-Users-roberto-sousa-Documents-Projects-sidekick/memory/`).

Patterns it reported, each marked by its cause:

1. **No lifecycle.** A note is retired in the index, not in the note, so a reader who opens it by link or grep meets stale claims.
2. **No lifecycle.** Supersession is recorded on one side only.
3. **No lifecycle.** Rulings that shipped into a skill stay in memory too.
4. **Parallel sessions.** A shared log passes work between sessions. On 2026-10-11 at least four sessions appended to `restructure-2026-09.md` with `cat >>`.
5. **Parallel sessions.** A fact lives in the note of the session that learned it. The session that closed #144 logged it in `restructure-2026-09.md`; a later session edited the rule-conflicts note and left "#144 backlog".
6. **No lifecycle.** A problem is patched with a banner: the same paths note was prepended to eight notes instead of fixing the paths.
7. **Tooling.** 17 notes carry a missing or stale `modified` stamp. Edit-tool writes update it; Bash writes do not.
8. **Scope.** Facts true in every repo load only in sidekick sessions.

It found no two sessions writing memory at the same time since 2026-09-20. The parallel-session failures here are handoffs through shared notes, not races.
