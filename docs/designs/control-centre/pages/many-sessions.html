You asked: in process or another one?

Each background session is its own process

I started a background session called bg-probe from this session's shell, then read the process table measured. It does not run inside the session that started it. A supervisor daemon owns it, and agent view only displays what the supervisor runs docs.

Your questions, one row each

What the probe and the docs settle

In process or another one?
Another process, under the supervisor. It keeps running when you close the terminal or agent view, and survives sleep. A shutdown stops it measured docs.
Scoped to the main session's folder?
No. It runs in the directory you dispatch it from, and that can be any repo: cd there and run claude --bg. Before its first edit it moves into its own git worktree under .claude/worktrees/, so parallel sessions don't collide docs.
Same hooks?
Yes. The probe ran your SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, and Stop hooks, the same ones this session runs measured. It reads settings from its directory as an ordinary session would docs. So a context monitor shipped in sidekick would cover background sessions too.
Context management inside one?
It's an ordinary session with its own window and the usual auto-compaction. Each one starts at about 74k tokens in this repo; where context goes breaks that down measured.
Does it touch the main session?
No. There is no "main session" in Claude Code's model. All sessions are peers, and the one in front of you is the one you're attached to. They meet only through files, git, and explicit messages.
Can I join one and take over?
Yes: claude attach <name>, or Enter in agent view. ← on an empty prompt hands it back, still running. Only one process can drive a transcript at a time docs.
Can an orchestrator do it?
Yes, within limits. A session can start one with claude --bg measured, read every session's state with claude agents --json, and message it with SendMessage. The docs name this use directly: "another Claude session that supervises background work" docs.
You asked: one orchestrator, one view, join any session

The orchestrator pattern works, and you are the tiebreaker

What you described maps onto real primitives. The orchestrator reasons and dispatches. Workers run in their own processes and worktrees. You watch one list, and attach when a worker needs a human.

# from the orchestrator, or from your shell
claude --bg -n "worker-142" --model opus --effort high "Run the plan in docs/superpowers/plans/…"
claude agents --json --all   # state, status, waitingFor for every session
claude attach worker-142     # take over; ← on an empty prompt hands it back
claude logs worker-142       # recent output without attaching

What holds

  • Each worker has its own context. The orchestrator's window grows only by what it reads back.
  • The orchestrator can ask for one idle notice per worker. That costs no tokens in the watched session docs.
  • Each session can run on a different model and effort docs.
  • Worktree isolation happens automatically inside a git repo docs.

Where it stops

  • A message can't approve a permission prompt, and a slash command in a message arrives as text docs. A worker blocked on a permission waits for you to attach.
  • By default, a session that bypasses permissions holds incoming messages for your approval, unless the sender bypasses too. crossSessionInbound overrides that docs.
  • Nothing stops the orchestrator messaging a worker you've attached to. The two of you share the wheel until you hand it back.
  • Agent view is a research preview, so keys and behaviour can change docs.
  • Deleting a session in agent view deletes the worktree Claude made for it. Commit first docs.

What this means for sidekick's worker handoff

sk-execute says the operator opens a session and starts sk-worker there, then the orchestrator finds it with ListAgents. claude --bg turns that into one command, and the worker shows up in agent view. Two things to check first: whether a background session accepts /sk-worker as its first prompt unverified, and whether a worker's edits landing in an automatic worktree fits the handoff's branch rules unverified.

Where workflows help #140

A workflow keeps the control flow in code rather than in a model's context. That suits the loop's unattended stretches: execute, review each task, verify the whole branch. It runs in the background and reports back when done (Workflow tool description).

Where they don't

The pauses #140 lists are the operator's: outcome, seeds, design decisions, the mode choice. A script can't hold those. #140 already says to explore each pause before building. Workflows stay opt-in under your CLAUDE.md, so trying one needs your yes.

You asked: is the Ralph loop useful to us?

Ralph: take the lesson, skip the loop

The original

Geoffrey Huntley's shell loop feeds the same prompt file to a fresh agent process, over and over. State lives in files and git, not in the conversation.

while :; do cat PROMPT.md | <agent> ; done

Each run is a new process, so each starts with clean context estimate: that follows from the loop's shape, as reported by secondary sources.

Anthropic's plugin

ralph-loop in claude-plugins-official uses a Stop hook. When Claude tries to stop, the hook feeds the same prompt back in the same session, until a completion phrase appears or an iteration cap hits docs.

Same session means the context keeps growing. It drops the original's most useful property.

What to take

  • Fresh context per unit of work, with files as memory. That is your worker idea, and background sessions make it cheap to run.
  • A completion check a machine can run. Tests, a gate, a stated "done" condition. That is what lets any loop run without you.
  • An iteration cap. Every loop gets one. sk-agent-prompts Rule 11, "cap every loop", already asks the same of sidekick's own loops.

What to leave

Ralph trades review for throughput and usually runs with permissions skipped. #140 records that you value quality over speed, so its pauses deserve the exploration #140 asks for before any loop replaces them.

You mentioned: Moltamp for Claude Code, iTerm2 for the rest

Moltamp wraps the same binary you run now

From its site: a skinnable macOS shell that spawns your own claude. Tabs glow amber when a session needs a decision and green when it finishes, with up to 50 sessions. It is free with a nag, or $10. It sends anonymous usage stats with a machine fingerprint you can turn off. The site names no maker and states no licence for the app docs.

As a terminal, it sees everything your sessions print. That matters for incident work that shows production data estimate. Agent view gives the same "who needs me" signal from Claude Code itself, so it's worth a week before adding a third-party layer.
