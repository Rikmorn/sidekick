Where Memory Lives

Fresh context per unit of work works when every fact has a home with a scope and an end. Your memory problems are mostly facts in the wrong home, at the wrong scope, with no end.

This page answers three questions: what “files as memory” looks like in practice, what is going wrong with your memory today, and whether memory should be scoped per profile. It maps the problem and stops short of a design.

You asked: what does “files as memory” look like?

One unit, one fresh session, five kinds of file

Ralph and Anthropic's long-running harness converge on the same loop. A session starts empty, reads a few files, does one unit of work, writes back, and ends. Its context is disposable because everything that matters has left it as a file source.

The rule both sources repeat

Keep status out of the always-loaded layer. Huntley's prompt says “DO NOT PLACE STATUS REPORT UPDATES INTO @AGENT.md”. Farr's playbook: “A bloated AGENTS.md pollutes every future loop's context.” source

Structured state survives better

Anthropic chose JSON for its feature list because the model “is less likely to inappropriately change or overwrite JSON files compared to Markdown files.” Its prompting guide says to consider a fresh context over compacting. source

Why it rots

Five causes, each with evidence

Wrong home

Memory holds project state and history that your conventions put in issues, ADRs, and learnings. sidekick's own memory says “derive state from sidekick pm pickup, not from here”.

Evidence: 10 index lines in sidekick flagged historical, superseded, or stale; one index line runs to 2,905 characters measured.

Wrong scope

There is one store per repo, shared by every kind of session in it. Facts about you are trapped per repo, and an incident session would write next to feature work.

Evidence: “per repository, shared across worktrees” docs; user and feedback notes split across repos measured.

No forgetting

Nothing expires. A superseded fact stays, marked in prose. Claude Code's reminder fires only near the size limit. Selective forgetting is unsolved in research.

Evidence: MemoryAgentBench finds current methods “fall short” on forgetting; mem0 dropped automatic updates in April 2026 source.

Parallel writes

Plain-markdown memory has no locking. Parallel sessions in one repo share one folder, so a later write can overwrite an earlier one.

Evidence: both surveys found concurrency handled only by daemons, locks, or hash checks, and not by plain markdown source. Overwrites on your machine are unverified.

Untrusted writes

A session that reads untrusted text can write it into memory, and every later session trusts it. That is the prod-issues case: alert payloads.

Evidence: a 2026 paper reports 81.7% cross-session attack success against Claude Code once memory is poisoned (arXiv 2609.13889) source.

Research names the reading-side harm too. Chroma measured performance falling as input grows, even with one distractor. Breunig calls the failure modes poisoning, distraction, confusion, and clash source.

The counterargument to buying a tool

Letta benchmarked an agent with only files: 74.0% on LoCoMo, against Mem0's reported 68.5%. It concluded that how well the agent uses the store matters more than the store. Manus keeps context append-only and errors visible. Cognition argues that isolating context loses implicit decisions source.

Your hunch: memory scoped per profile

The evidence agrees, with a twist

What supports it

  • autoMemoryDirectory can be set from --settings, so a profile can point memory at its own folder docs.
  • Anthropic's Managed Agents guidance: “Use focused stores … one per user, one for shared domain knowledge, and one for project-specific context.” source
  • The Claude app keeps a separate memory per project, and Willison objects to unscoped recall source.

The twist

  • Claude Code gives a session one auto-memory folder. Point it at a profile folder and every repo's notes for that profile merge, so project scope is lost inference.
  • The docs show no per-repo placeholder in the path. A launcher could compute one, for example profile plus repo unverified.
  • Several scopes at once (you, profile, project, unit) need either composition or a store that attaches several, as the API does.
  • Context and memory are different levers. A profile already scopes what loads; memory scoping decides what persists and who may write.
“update an existing note rather than creating a duplicate; delete notes that turn out to be wrong.” Anthropic's prompting guidance for Claude Fable 5.
What would let you formalise it

Questions, then experiments that answer them

Questions only you can answer

  1. What should each profile remember that the others should not?
  2. Who may write memory: any session as it goes, or only a promotion step you review?
  3. When does a fact end: when its unit closes, when it's superseded, or at a periodic review?
  4. Should a session that reads untrusted input, such as prod-issues, write memory at all?
  5. Where do facts about you live, so that every session sees them?

Experiments that produce evidence

  1. Audit one memory folder. Classify each entry by scope and right home, and count how much is misplaced, stale, or general.
  2. Test autoMemoryDirectory in a profile. Check whether the index loads from there and whether writes land there.
  3. Test a read-only shared file. Check whether a profile can load notes, for example through an import, without the session writing to them unverified.
  4. Watch two parallel writers. Run two background sessions in one repo, each asked to save a memory, and see what survives.
